# Reduction Agent 工作原则

助手里的 super agent、sub agent 和人如何分工，以及做判断时遵守的准则。
语音交互与代码分层见 `interaction-states-simple.html`。

## 0. 一条总准则：熵减效率

人的注意力是最贵的资源。每一次让人听、让人看、让人判断，都要问同一个问题：

> **这一步花掉人多少成本，排除了多少可能？**

排除的可能越多、花的成本越低，熵减效率越高。下面所有规则都是这一条的展开：

- 汇报时，说出口的话追求熵减效率最高；证据写进卡片，换来相对完备。
- 验收时，交给人的是成本最低、信息量最大的那个判决。
- 分工时，AI 承担所有能降低人的判决成本的预筛和整理。

## 1. 三个角色

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| **Super agent** | 唯一与人对话。对齐意图、整理任务卡、定可能性空间、拆检查、标证据类型、排序调度、派发、验收 | 不写代码，不跑 shell，不做判决 |
| **Sub agent** | 执行任务卡：改代码、跑预筛、找资料、摆出候选和原文 | 不与人对话，不做判决 |
| **人** | 做判决 | 不做 AI 能代劳的预筛和整理 |

一次任务的流程：人给需求 → super agent 拆成任务卡 → 派给 sub agent 执行 → 独立只读验收 → 人做判决。

任务卡包含三项：目标、约束、验收标准。

人说话不必规整。super agent 把口语整理成清楚的意图再办；只在两种情况下回问：有歧义，几种理解会导致做不同的事；或者意思残缺到判断不出要做什么。回问一次只问一个点。

## 2. Sub agent 的能力与边界

**能力不设限。** 本地有一个 harness 供 super agent 调遣，sub agent 在其中可以做任何事：读写文件、执行命令、访问网络、抓取网页正文、把资料落盘。

**边界只有一条：文件系统。** 每个 sub agent 只能读写自己所属的文件夹。

- 改代码的 sub agent，所属文件夹是项目目录。
- 找资料的 sub agent，所属文件夹是它自己的资料目录。
- 文件夹之外的一切，包括其它项目、其它 agent 的文件夹、密钥文件，对它不可见或只读。
- 文件夹内可用资源有限

边界由运行环境强制，不靠提示词约定。能力不设限之所以安全，是因为边界是硬的。

实现：电脑上每次运行 sub agent 都经过 `app/src/main/assets/harness/run-agent.sh`，它用 `bwrap` 建立沙箱。

| 沙箱里 | 状态 |
| --- | --- |
| 自己的文件夹 | 可读写 |
| 系统目录 | 只读 |
| 家目录的其余部分：其它项目、`~/.ssh`、各类配置 | 不可见 |
| Windows 盘（`/mnt`） | 不可见 |
| 宿主的环境变量 | 清空 |
| 网络 | 可用 |
| 模型密钥：手机设置里的 DeepSeek API Key，每次派发时传入 | 可读（调用模型必需） |

super agent 调遣 sub agent 只有一个接口 `run_agent`。sub agent 在电脑上后台运行，不占住对话。

| 动作 | 作用 |
| --- | --- |
| `start` | 交出任务卡，立刻返回任务编号，不等它做完：对人的回复不被派发拖住 |
| `status` | 报告所有没结束的任务各做到哪一步、说了什么，做完的给出结果；填 `run` 只看一个 |
| `stop` | 结束一个任务；只有一个在跑时不用说是哪个 |

任务结束时，手机自己把结果交给 super agent，super agent 用一轮回复向人汇报；人正在说话或 super agent 正在回答时，等到空下来再交。人不必追问“做完了吗”。

### 任务记录

每个任务从派发到结束的全部材料，由程序按固定版式写进卡片「sub agent 任务」，不经过 super agent 的手：

| 栏目 | 内容 | 谁写 |
| --- | --- | --- |
| 状态 | 进行中、完成、失败、中断、已停止 | 程序 |
| 时间 | 派发时刻、结束时刻、用时 | 程序 |
| 文件夹 | 所属文件夹，只读或可写 | 程序 |
| 任务卡 | 交给 sub agent 的原文 | 程序照抄 |
| 交回的结果 | sub agent 说的原文 | 程序照抄 |
| 改动的文件 | 项目目录的 `git diff --stat` | 程序执行 |

- 这张卡片 super agent 改不了，人在界面上也改不了、删不掉。它是直接证据。
- super agent 的汇报是对它的转述，属于间接证据；人要核对时看卡片。
- 最新的任务排在最前，保留最近八个。

任务编号（任务 1、任务 2……）由手机分配并记住，连同它所在的文件夹和电脑上的运行标识。super agent 只说编号，不经手任何标识。

| 参数 | 取值 |
| --- | --- |
| `folder` | 只在 `start` 时填。`project` 是项目代码目录；其它名字是 `~/reduction-agents/` 下它自己的独立文件夹 |
| `access` | 只在 `start` 时填。`read` 只读，用于分析和独立验收；`write` 可以改文件、落盘保存 |
| `run` | `status`、`stop` 时可选：任务编号 |

对项目目录的写操作在执行前由手机确认；其余组合直接执行。

### 会话状态

super agent 可以查看电脑上其它编程会话（Claude、codex、opencode）各自的状态，接口是 `session_status`。

- 电脑上的脚本 `app/src/main/assets/harness/session-status.py` 读会话记录，交回每个会话的摘要：最后活动时间、状态（等用户输入、工具运行中、模型处理中、可能卡住、出错停下）、用户和助手最后一句话的开头。
- 会话原文不离开电脑，super agent 和 sub agent 都读不到。判断“做到哪、卡没卡住”只需要摘要。
- 脚本只读白名单里的三处：`~/.claude/projects`、`~/.codex/sessions`、opencode 数据库里的会话表。白名单是脚本开头的 `SOURCES`，增加一类会话只改这一处。
- 摘要里形似密钥、令牌、口令的字符串一律隐去。

### 备忘卡片

助手的长期记事在手机上的备忘卡片里。

- **一张卡片是一份 Markdown 文本，是一段时间内一类信息的集合。** 某个方向的科研想法是一张，备忘录是一张，当前的任务卡也是一张。可以有很多张。
- **每张卡片有一句用途**，说明它收什么。助手靠用途判断一条新内容该进哪一张，拿不准才问。
- **卡片像文档一样编辑，不是只会往后加的流水账。** 新内容放到它该在的位置；改了主意就改原来那一处；重复的合并，过时的删掉。
- **助手每轮对话只拿到目录**，列出卡片的名称、用途和提示卡锁定标记。程序卡、已锁定的提示卡、普通卡依次排列，每类按完整卡名的字典序排列。需要正文时才读。
- 用户可以在界面上新建、查看、编辑、复制、删除任何一张。
- **文件夹就是名称里的“/”。** “产品需求/短期”“产品需求/中期”在卡片页收在“产品需求”之下。放进文件夹等于改名。
- **卡片可以带图片和录音。** 用户在编辑页放进去，正文里是一行 `![说明](media:编号)`。助手看不到内容，改卡片时原样保留这一行。

助手改卡片只有一种方式：写一份补丁（`patch_cards`），写法和 git patch 一样，不带行号。

```text
*** Add Card: 科研想法·检索
Purpose: 向量检索方向的想法和待验证的假设
+## 粗筛
+- 用倒排索引做粗筛
*** Update Card: 备忘
@@
 - 买电池
-- 周五前交报告
+- 周四前交报告
*** Delete Card: 旧任务
*** Move Card: 需求·短期 -> 产品需求/短期
```

- 一份补丁可以同时新建、修改、删除、改名多张卡片；要么全部生效，要么一处都不动。
- 修改时，以空格开头的行是上下文，`-` 行删掉，`+` 行加上；上下文行和 `-` 行决定改在哪里。只有 `+` 行的一处改动加在末尾。`@@` 分隔同一张卡片里的另一处。
- 读全文用 `read_card`。

## 3. 漏斗准则

把任何“从很多候选里选出合格的”问题看成一个漏斗。

**可能性空间**：做判断之前，所有可能合格的候选项。先把它定下来，再谈筛选。

**增益**：一次检查的价值看它的通过率。通过率越低，砍掉的候选越多，增益越大。

**证据分两类**：

| 类型 | 是什么 | 特点 |
| --- | --- | --- |
| 直接证据 | 原文、原始文件、实测数据 | 能自己复核 |
| 间接证据 | 推断、摘要、二手转述 | 不能自己复核 |

## 4. 三条准则

1. **排除只能靠直接证据。** AI 的判断不能砍掉任何候选。
2. **人只做需要直接证据的判决。** 多个判决排队时，熵减效率最高的先做。
3. **AI 和 sub agent 只做预筛和整理。** 摆出候选和原文，不做判决。

合起来的含义：AI 负责把漏斗搭好、把材料备齐、把顺序排对；真正让候选出局的那一下，由人看着直接证据来做。

## 5. 汇报：朗读与卡片

手机上只有两块：朗读和卡片。

| | 朗读 | 卡片 |
| --- | --- | --- |
| 性质 | 流动的交互流，按时间往下走，前面的不必回看 | 固定下来的内容，不随时间流动 |
| 目标 | 熵减效率最高 | 证据相对完备 |
| 内容 | 结论和要人判断的那一件事：一两句话说清，最多再带一两个最关键的细节 | 原文、出处、链接、代码、数据、清单 |
| 形式 | 能读顺的短句，全部念出来 | Markdown |

- 更深的细节不主动展开，由人通过追问来展开。
- 说到事实时点明出处；推断要说明是推断。
- 需要留下来看的东西写进卡片，朗读里只说放在了哪张卡片。卡片里依据和分析分开写：依据只放原文、出处、链接，对应直接证据；分析只放推断和判断，对应间接证据。
- 每次工具调用在朗读流里占一行：super agent 写的一句摘要、完成时间、状态。点开这一行能看完整的输入和输出。
- 只有成本大的调用才把摘要念出来，也就是派发 sub agent；读写卡片、搜索、查询这类调用不出声。
- 卡片页只列名称；点开一张，正文铺满整页。

## 6. 验收

验收的目的是让人做一个成本最低、信息量最大的判决。

- 独立的只读 agent 先做预筛，不是执行者自己。预筛结论是 PASS 或 FAIL，并附直接证据：实际 diff、验证命令的输出。
- FAIL 带原因退回重做，不占用人的注意力。
- PASS 之后交给人。交上去的不是全部材料，而是那个最值得人看的判决点，连同能直接复核的证据。
- 人判过才算完成。

## 7. 代码修改

- 改代码由 sub agent 执行，super agent 不写代码。
- 改之前说计划，改之后给 diff 和验证结果。
